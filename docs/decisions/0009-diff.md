# 0009 — Recording operations from an edited file

Decision 0007 decided how operations are read, replayed, and merged, and said
nothing about how they are written. That is the half a person actually uses:
they edit a file and expect the tool to work out what they did.

This is numbered 0009 because 0007 promised the tree to 0008, and a promise in
a decision outranks the convenience of the next free number. The order is not
otherwise meaningful: a diff works on one file's items and needs no path, so
nothing here waits on the tree.

## The decision

A revision's operation document is produced by diffing the file at that
revision's parent state against the file as it now stands, at the line
granularity 0007 fixed. The decomposition that produces is recorded once and
never recomputed.

The line matching comes from `similar` 3.2 with `Algorithm::Histogram` and no
deadline. Everything between that and the stored bytes — anchoring, coalescing,
terminators, and the canonical spelling — is Historica's, is specified below,
and is the part worth reviewing.

## The diff is a tool decision, and this is the only place that is true

0007 already established why: the decomposition "must be recorded once by the
person who made the edit rather than recomputed by whoever reads it". Two
replicas therefore never diff one pair of files independently and have to
agree. A different-but-valid decomposition is not a divergence — it is a
different account of how the same bytes came to be, and both are legitimate
history.

That is exactly what a merge rule cannot say, and it is why a dependency is
defensible here and would not be there. Merge semantics have to be identical
everywhere or old histories change meaning; a diff only has to be *good*.

So the objective is not a minimal edit script and not tidy hunks. It is
**decompositions that merge well**, because every operation this produces is a
permanent event in the graph that all later merges are computed against.

## What any diff must produce

Four properties. The first is the acceptance oracle and the rest are the
format's own rules arriving at the writer:

- **`apply(parent, diff(parent, child))` is `child`, byte for byte.** Anything
  else is a bug, whatever it looks like on screen.
- **The output parses.** Ascending positions, no overlap, adjacent deletes
  merged into one, `delete` before `insert` at one position. The parser is the
  judge of this, so the writer's tests hold it to the parser rather than to a
  second copy of the rules.
- **`diff(x, x)` produces no document at all.** An absent fact is an absent
  line, and 0007 says a revision that changes nothing about a file names no
  operation document. An empty one would be that fact spelled twice.
- **The same pair of files produces the same bytes on any machine.**

The last one is not free, and it is the reason for one specific configuration
choice. `similar`'s algorithms are deadline-aware: given a deadline, they check
it periodically and "may fall back to a simpler script instead of running too
long". A timeout would therefore make the recorded decomposition a function of
how fast the machine was that day, and the corpus that pins these bytes would
fail on a slow one — for a reason nobody chose and nobody could reproduce. The
crate's default is no deadline. Historica must never set one, and the test that
says so belongs with the code rather than in this paragraph.

## Histogram, on a measured preference rather than a story

This section's first draft argued that a minimal script keeps an incidental
blank line between two rewritten paragraphs alive as an item, and that
histogram avoids it. **That claim is withdrawn: it is not what happens.** A
blank line appearing once on each side is the best anchor in the file by every
algorithm's reckoning, and Myers, Patience, Histogram and Hunt all keep it.
No line-granularity matcher drops it. The merge consequence is real — an item
with an identity survives in the middle of text its author replaced, and
concurrent edits can anchor to it — but it is a cost of the line granularity
0007 chose, not of any algorithm available underneath it.

What can be measured is in `examples/matchers.rs`, which generates
prose-shaped edits — paragraphs separated by blank lines, drawn from a small
vocabulary so that repeated lines are common — and compares every algorithm on
the same pairs. Over 3000 random edits:

| Algorithm | Differs from Myers | Operations | Items touched |
| --- | --- | --- | --- |
| Myers | — | 7623 | 19457 |
| RawMyers | 0% | 7623 | 19457 |
| Patience | 9.1% | 7583 | 19975 |
| Histogram | 12.1% | 7485 | 19531 |
| Hunt | 11.7% | 7591 | 19457 |

Two things follow. Myers and RawMyers never disagree on this shape of input, so
the heuristics `similar` adds to Myers cost nothing here. And where the
anchoring algorithms differ, histogram records the fewest operations — 1.8%
below Myers — while touching about the same number of items, where patience
buys a similar reduction in operations by matching 2.7% less of the file.

Fewer operations is the metric that matters, for the reason the next section
gives: every operation is a permanent event, and a concurrent edit interleaves
*between* operations rather than inside one. Histogram is chosen on that
margin.

The margin is small and is recorded as small. On roughly seven eighths of these
edits every algorithm produces the same decomposition, so this is a weak
preference with a measurement behind it rather than a strong result. It is also
why the choice sits behind one constant.

## Runs are maximal

Contiguous inserted items become one `insert`, and contiguous deleted items one
`delete`. The format already forces this for deletes — two that meet are
refused — and it is chosen for inserts.

The reason is Fugue. Its guarantee against interleaving is strongest inside one
insert run: N separate one-line inserts give a concurrent edit N places to
interleave that a single N-line insert does not. Splitting a run buys nothing,
because there are no hunks in this format, no context lines, and no `@@`
headers to make readable.

## A replacement anchors at the removed run's start

0007 left this ambiguous, and the ambiguity is now in the corpus. Its prose
says:

> At one position, `delete` precedes `insert`. A replacement is then spelled
> the way every diff spells it, minus lines above plus lines.

which describes `delete P N` followed by `insert P`. Its worked example — which
is `tests/corpus/operations/02-concurrent.ops` byte for byte — spells the same
replacement `delete 3 1` followed by `insert 4`, anchored past the removed run.
Both parse, and they are different operations: they name different gaps, so a
concurrent insert at that boundary lands on a different side of the new text.

**A replacement this tool records is `delete P N` then `insert P`.** It matches
the prose; it is the spelling the parser's tie-break rule exists for; it keeps
replacement text attached to what precedes the removed run, which is where the
person was writing; and it is what `similar` reports without being asked, since
a `Replace` carries one `old_index` for both halves and the alternative would
mean inventing a second position.

The corpus keeps 0007's example as it is. The parser must accept both anchors
— documents written by other tools, and by this one before this decision,
exist — so the file stops being an inconsistency and becomes the corpus's
example of the anchoring this writer does not produce. A test says so, in
those words, rather than leaving it to look like an oversight.

## Terminators need no special case

An item is a line including whether it ends with a newline, so a file that
gains or loses its final newline differs from its parent *in that item*. The
matcher sees two different items and records a replacement of the last line
without anything being taught about terminators.

That is also the linear half of 0007's third open question. Appending to a file
whose last line had no terminator is spelled as rewriting that line and then
adding the new ones — which is exactly what replay already demands, since a
result holding an unterminated item anywhere but at the end is refused. The
concurrent half of that question, where two branches assert different things
about one last item, stays open where 0007 left it.

## Rejected alternatives

**Implementing the matcher in Historica.** This document's first draft chose
it, on the ground that a dependency could change the decomposition underneath
us. It cannot: the version is pinned, an upgrade is somebody typing
`cargo update`, and the corpus files pinning decompositions fail loudly when
they do. What remained was several hundred lines of well-solved, fiddly code
with subtle failure modes and no argument for owning it. The shaping layer —
anchors, runs, canonical spelling — is Historica's and is written here, which
is the part that was ever really ours.

**Myers, minimal.** Above. Worth adding that its `RawMyers` variant, which
disables the heuristics, is *more* minimal and no better here for the same
reason.

**Patience.** Above. It would be the right answer for source code, and this is
not primarily a tool for source code.

**Letting a person choose the algorithm**, per repository or per commit. The
recorded decomposition would then depend on configuration that is invisible
from the file, which is the property this project spends its effort avoiding.
When the algorithm changes, it changes for a version of the tool; documents
already written are unaffected, because they are already written.

**Move detection.** 0007's vocabulary has two operations and no move, so a
moved paragraph is a delete and an insert. Recorded here as rejected rather
than merely absent, because a reader who knows Darcs will look for it.

**Diffing against the superseded revision when amending.** An amendment's
parent is the parent it always had, so its operations are stated against that
same state and the diff is parent-to-file like any other. Nothing about
rewriting a change makes the old revision a parent — 0001 keeps supersession in
a second DAG, separate from the parent edges that carry causality — and
treating it as one would record operations no replay could apply.

## Consequences

- `src/` gains a `diff` module, and `Cargo.toml` its second dependency:
  `similar` 3.2, default features, Apache-2.0, which is compatible with this
  project's MIT-or-Apache. It brings no transitive dependencies.
- `Cargo.lock` becomes load-bearing for reproducing a *recording*. It is not
  load-bearing for *reading*: a store already written does not care what
  produced it, which is the whole point of storing the decomposition.
- The acceptance test is a property test over random parent and child pairs:
  the round trip is exact, the output parses, and identical files produce
  nothing.
- The corpus gains examples for the choices a property test cannot see — the
  anchoring of a replacement, a file that gains and then loses its final
  newline, and the line that survives between two rewritten paragraphs, pinned
  so that a known cost stays known.
- 0007's open question 3 has its linear-case answer.

## Open questions

1. **Whether histogram survives conformance testing.** 0007 owes a conformance
   suite against the Eg-walker reference implementation, and the interaction
   between decomposition quality and interleaving is empirical. If a
   decomposition that anchors differently interleaves visibly less, this
   choice should move, and it can: it changes what future revisions record and
   rewrites nothing.
2. **Whether a diff should ever decline.** A file replaced wholesale produces
   one delete and one insert, which is correct and says nothing. Whether a tool
   should notice that and ask the person whether they meant to replace the file
   is an interface question, not a format one.
3. **Binary and non-UTF-8 content**, deferred by 0007 and still deferred. A
   list of lines is the wrong model for an image, and a diff over it is the
   wrong writer.
