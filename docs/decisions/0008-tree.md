# 0008 — The tree: files, paths, existence, and rename

Decision 0007 took content without introducing a path, and named this document
for the rest: "paths, directories, existence, and rename become 0008". Decision
0003 sent the same list here, and 0002 left a question here about paths that
are not valid UTF-8. This answers all of it.

It is written after 0009 because 0007 promised this number to the tree and a
promise in a decision outranks the convenience of the next free one.

Most of what follows is not a free choice. Three earlier decisions constrain
this one so tightly that the interesting work was finding what they already
imply, and saying where they stop.

## The decision

A revision records what it did to the file set, in the shape 0007 chose for
content: what changed, never what is. Files have identities of their own, and a
path is a fact *about* a file rather than the file's name. The facts are
headers in the revision document; there is no separate tree object.

```
historica-v0
change qpvuntsmwlrkzxonmvtplsyq
author Adam Harris <adam@example.com>
when 2025-08-19T00:47:11-06:00
add lqxstvnmpkwyzrolvtsqnkxm notes/2025-08-19.md
move ptkwnrvzlmyxqsotnkwlpvzr notes/archive/2025-08-01.md
drop wnkyzrtlmqvsxopwnztkylrv
edit lqxstvnmpkwyzrolvtsqnkxm 1e4e224e93380a25d4cd1be85d35db37f4064be4388822eba250894c6d6daa0d

Start a journal and file last month's entry
```

| Header | Meaning |
| --- | --- |
| `add <file> <path>` | The revision brings this file into existence, there. |
| `move <file> <path>` | The revision changes where it sits. |
| `drop <file>` | The revision removes it. |
| `edit <file> <digest>` | The operation document this revision contributed to it. |

They come after `revised` and before `x-`, and each is repeatable and sorted by
value under 0002's rules — which sorts them by file, because the file comes
first on the line.

## A snapshot per revision was never available

Git names a tree object that lists every path in the repository, and shares
subtrees between revisions so that restating them is cheap. That is a
consequence of storing snapshots, and this store has none to share: writing the
whole file list into each revision would put every path of a repository into
every revision document. A journal of five thousand entries would restate five
thousand paths to record a typo fix, in a file a person is supposed to read.

So the tree records changes, like content does. This is not really a second
application of 0007's argument — it is the same argument arriving somewhere
else.

## Files are identified, and 0001 already decided how

A rename must not lose a file's history. If a path were the file's identity,
renaming would be a delete and a create, the operation chain 0007 depends on
would break at every rename, and recovering the connection would mean matching
content at read time — a heuristic, which is the class of thing 0002 and 0007
each refused for the same reason.

So a file carries an identifier, and paths hang off it. The identifier is spelled
exactly as a change ID is: 24 characters of `k` to `z`, 96 bits, an alphabet no
digest can be mistaken for. One alphabet to learn, and 0001's argument for
minting rather than deriving it applies here word for word:

> A derived identifier changes when the thing is rewritten.

A file identifier derived from its creating revision — that revision's digest
and an index, say — would change the moment that revision was amended, and
every later `move`, `edit`, and `drop` naming it would be naming nothing. The
same reasoning that made a change ID assigned makes a file ID assigned.

Two replicas that create "the same" file separately mint two identifiers and
have two files. That is correct: they are two files, and the merge below says
what happens when both want one path.

## There are no directories

A path is a string of components separated by `/`. A directory exists exactly
when some file's path names it, and nothing records directories otherwise.

The cost is two things, and both are worth paying. **An empty directory cannot
be represented** — Git has the same limitation, so it is at least a familiar
one. And **moving a directory is renaming every file beneath it**, one `move`
line each, rather than one line naming the directory.

What that buys is the absence of the hardest problem in this area. A tree of
nodes that can be moved into each other can be made to cycle by two concurrent
moves — A into B on one replica, B into A on the other — and the published
solutions to that (Kleppmann and others, 2021) are algorithms with their own
metadata and their own undo semantics. A flat set of paths cannot cycle,
because a path is a value and not an edge. Renaming a directory of fifty files
writes fifty lines, once, in a file that already records what it did.

## Paths are UTF-8, which closes 0002's third question

0002 asked how paths that are not valid UTF-8 would be spelled, and hoped for
"an escape that is visible only when needed" rather than quoting every path
forever.

A path is valid UTF-8, and there is no escape. Beyond 0002's existing rules for
a header value — no control characters, no leading or trailing space — a path:

- has `/` between components and no empty component;
- has no component that is `.` or `..`;
- neither begins nor ends with `/`;
- treats `\` as an ordinary character, because this is a path in a format, not
  a path on Windows.

What this refuses is a filename whose bytes are not UTF-8, which a person
cannot type, display, or check by eye — the properties this project exists to
keep. The cost is real and narrow: an existing repository holding a Latin-1
filename cannot be imported without renaming that file.

The escape 0002 wanted is left designed but unbuilt, because 0004 guarantees it
can arrive later without breaking anything: a `path-bytes <file> <hex>` header
would carry the original bytes for the files that need it, be ignored by
nothing, and leave every ordinary path unquoted. If importing such a repository
ever becomes a real need rather than a hypothetical one, that is its shape.

Two paths that differ only in Unicode normalisation, or only in case, are two
paths here and one file on macOS or Windows. The format compares bytes; `check`
reports the collision as a note, in 0006's sense — a real hazard that is not the
store contradicting itself.

## What an entry may point at

A file's content is the operation chain its `edit` lines name. 0007 deferred
the other case here:

> **Binary and non-UTF-8 content.** A list of lines is the wrong model for an
> image. The likely answer is that such a file names its bytes and never
> merges, which is a tree question about what an entry may point at.

It is that, and the shape is decided now even though the implementation is
deferred: `bytes <file> <digest>` names a file's whole content, stored under
`history/bytes/` by digest like everything else. Such a file has no operations
and never merges — two concurrent `bytes` lines for one file are a divergence
to report, exactly as 0001 describes divergence, and never a silently chosen
winner.

A file is one kind or the other. Changing kind is `drop` and `add`, because a
file whose content model changed underneath its identity would make every
earlier operation in its chain unreplayable while still being named by it.

## What one revision may say about one file

Exactly one of these, per file, per revision:

- `add`, alone or with `edit` or `bytes` — a file created, empty or with
  content;
- `move`, alone or with `edit` or `bytes`;
- `edit` or `bytes` alone;
- `drop` alone.

`add` with `move` is a path stated twice, and the fix is to `add` at the final
path. `drop` with `edit` is a contradiction. A file dropped and added again in
one revision is refused: a resurrection is a new file, with a new identifier,
which is what it is anyway once anyone has merged the drop.

## Merging the tree

The tree at a set of heads is computed by replaying tree facts in causal order,
as content is. Concurrency is resolved by rules, not by asking:

- **A `drop` concurrent with an `edit` or a `move` loses.** The file survives,
  with the edits. Losing work is worse than keeping a file somebody wanted
  gone, and the person who dropped it can drop it again knowing what they now
  have. Reported as contested.
- **Two concurrent `move`s** resolve to the path from the revision whose digest
  sorts lower. By digest, because 0007 fixed that: not by timestamp, which 0002
  refuses to trust, and not by change ID, which 0001 calls an unverifiable
  claim. Reported as contested.
- **Two concurrent `drop`s** agree, and the file is gone. Nothing to report.
- **Two files claiming one path** both keep their identities, and the path is
  reported as contested. Neither is renamed by the format, because a name
  invented by a merge is content nobody wrote — and because 0003 already
  established that a file's name in a directory is presentation. A working
  directory has to show both, and how it does that is interface work.

This is the same division 0007 drew and for the same reason: the algorithm
never fails, the tool may, and a merge a person records is a revision like any
other.

## Consequences

- The revision document gains `add`, `move`, `drop`, `edit`, and reserves
  `bytes`. A reader that does not know them is a version 0 reader that never
  existed, so 0004's vocabulary rule costs nothing here.
- `format` gains a file identifier — the change ID's spelling under another
  name — and path validation with an error per rule.
- 0007's requirement that "the tree must give a revision's files a total order"
  is satisfied by the order the revision document already writes: `edit` lines
  sorted by file identifier, operations numbered within each in document order.
  Operation identity is therefore stable under rename, which it would not have
  been had the order been by path.
- `check` can finally do what 0007 owed it — hold an operation document to the
  parent it edits — because the tree is what says which document belongs to
  which file.
- `store` gains `bytes/` when that half is built, and nothing before then.
- The corpus gains its first history of more than one file, and its first
  rename.
- 0002's third open question is closed, and 0003's list of deferrals is empty
  but for sharding.

## Rejected alternatives

**Paths as identity, with rename detection at read time.** Git's model. Rename
becomes delete-and-create, the content chain breaks, and the connection is
recovered by a similarity heuristic whose result depends on the tool that ran
it. 0002 spent a section establishing that two replicas must not disagree about
what a history says, and this would make "did that file get renamed" a question
two replicas answer differently.

**A separate tree document per revision.** Git's tree objects, minus the reason
for them. It would be a second document to name, dedup, and hold to the first,
whose whole content is what the revision document can state in four header
kinds — and since a revision states only what changed, the size that justifies
Git's arrangement never arrives.

**Directories as objects that can be moved.** Buys empty directories and a
one-line directory rename; costs the cycle problem, a move algorithm with its
own metadata, and a second kind of thing to merge. Not worth it for a format
whose paths are already strings.

**Derived file identifiers.** Refused for 0001's reason, above.

**Modes, symlinks, and an executable bit.** Not represented, and not for a good
reason so much as a narrow one: this is a tool for prose and journals, where a
mode is noise, and a mode is a fact about a file that `mode <file> <value>`
could carry later without disturbing anything. A repository of shell scripts
would notice before a repository of entries did.

## Deferred

- **Binary content**, whose shape is decided above and whose implementation
  waits until something needs it.
- **The working directory**: checkout, status, and how a contested path is
  shown to a person. All of it is interface work of the kind 0006 named.
- **Sharding**, still, which is 0003's fifth question and belongs to scale.

## Open questions

1. **Whether a `drop` should lose to a concurrent edit.** Chosen above because
   losing work is the worse failure, but a repository where deletion is the
   point — a redaction, a file that should not exist — would want the opposite,
   and the format cannot tell those apart.
2. **Whether two paths differing only in normalisation or case should ever be
   an error** rather than a note. It is a note here because the store is not
   contradicting itself; it is the filesystem that cannot hold what the store
   describes.
4. **What a revision that only renames costs a reader** who wants to know what
   a file's history is. The `move` lines are spread across every revision that
   touched the file, so answering "where has this file been" is a walk of the
   history rather than a lookup, until a cache makes it one.

## Resolved questions

3. **Whether a file may change kind** between operations and bytes without
   changing identity. Answered by [0017](0017-content-that-arrives-whole.md):
   kind is fixed when the file is added, because changing the content model
   would make its earlier operation chain unreplayable. A kind change is a
   `drop` and a fresh `add`; whether `record` should perform that pair is
   0017's fourth open question.
